# ExploreMHC_K562nWTC11

Comparing the MHC region between the K562 and WTC11 "personalized" genomes and
re-aligning CRISPR gRNA spacers against them, to find which GRCh38 MHC targets
are absent from a cell line's actual haplotype.

**[REPORT.md](REPORT.md) — findings from the guide-mapping analysis**: how
cleanly each guide maps in K562 vs GRCh38, why guides go missing, and whether
badly-mapping guides drive the manuscript's screen hits (they do not).

## Motivation

CRISPR screen libraries are typically designed against the reference genome
(GRCh38), but the MHC region on chr6 (~28–34 Mb) is one of the most polymorphic
regions of the human genome. A guide that matches GRCh38 perfectly may have no
exact target in the genome of the cell line the screen is actually run in. This
repo quantifies that loss for K562 hap2 and locates where in the MHC it happens.

## Approach

1. Extract 20-nt spacers from an IGVF guide table and trim the first base, so
   guides are compared as their 19-nt 3' portion (`trim1bp` throughout).
2. Align the unique trimmed spacers end-to-end with `bowtie2 -a` against both
   GRCh38 and the K562 hap2 MHC contig(s).
3. Keep only exact (`NM:i:0`), primary alignments and classify every guide as
   `Both`, `GRCh38 only`, `K562 MHC only`, or `Neither`.
4. Treat `GRCh38 only` guides whose target falls in chr6:28–34 Mb as "lost in
   K562", then bin them into 10-kb windows and cluster losses that fall within
   10 kb of each other.

## Usage

The whole pipeline is one command — it downloads the K562 hap2 MHC reference,
builds both bowtie2 indexes, and runs steps 1-4 below:

```bash
THREADS=16 bash exact_spacer_mhc_analysis_trim1bp.sh \
  IGVFFI2404DYFG.tsv.gz /path/to/hg38.fa analysis_trim1bp
```

The individual steps, if you want to run them yourself. `$SRC` is the IGVF guide
table (`.tsv.gz` with a `spacer` column).

```bash
# 1. unique trimmed 19-nt spacers + guide mapping
python3 extract_spacers_trim1bp.py "$SRC" spacers_19nt.fa spacer_map.tsv.gz

# 2. align against each reference (bowtie2 index built beforehand)
bowtie2 --end-to-end -a --no-unal -f -p 8 \
  -x grch38 -U spacers_19nt.fa -S sam/grch38_trim1bp.sam
bowtie2 --end-to-end -a --no-unal -f -p 8 \
  -x K562_hap2 -U spacers_19nt.fa -S sam/k562_trim1bp.sam

# 3. SAM -> exact-alignment tables
python3 parse_exact_alignments_trim1bp.py sam/grch38_trim1bp.sam GRCh38 \
  results/grch38_exact_alignments_trim1bp.tsv.gz
python3 parse_exact_alignments_trim1bp.py sam/k562_trim1bp.sam K562_hap2_MHC \
  results/k562_exact_alignments_trim1bp.tsv.gz

# 4. per-guide summary, clustering, and plots
python3 summarize_and_cluster_exact_trim1bp.py "$SRC" spacer_map.tsv.gz \
  results/grch38_exact_alignments_trim1bp.tsv.gz \
  results/k562_exact_alignments_trim1bp.tsv.gz results plots

# 5. where in the MHC the losses fall -- both default to the data files in the
#    repo root and write into results/, so they take no arguments
python3 analyze_intended_MHC_k562_losses.py   # by intended target coordinate
python3 analyze_k562_losses.py                # by realigned GRCh38 coordinate
```

## Adding a haplotype

K562 is diploid, so both haplotype assemblies matter: a guide is only absent
from K562 if it is absent from **both**. To align the spacers against a further
assembly and fold it into the lookup:

```bash
python3 extract_spacers_trim1bp.py data/IGVFFI2404DYFG.tsv.gz \
  spacers_19nt.fa spacer_map.tsv.gz
bowtie2-build --threads 8 data/K562.hap1.MHC.fa index/k562_hap1
bowtie2 --end-to-end -a --no-unal -f -p 8 \
  -x index/k562_hap1 -U spacers_19nt.fa -S k562_hap1_trim1bp.sam
python3 parse_exact_alignments_trim1bp.py k562_hap1_trim1bp.sam K562_hap1_MHC \
  data/k562_hap1_exact_alignments_trim1bp.tsv.gz
python3 build_guide_mapping_lookup.py
```

`extract_spacers_trim1bp.py` assigns `spacer_id`s by sorting the unique trimmed
spacers, so re-running it on the same guide table reproduces the exact ids used
by the existing alignment files — that is what lets the haplotypes be joined.

The two assemblies differ in completeness: hap1 is more fragmented (11 contigs
vs 4) and has a ~157 kb gap around chr6:31.75–31.91 Mb. The lookup measures each
haplotype's local coverage and sets `absence_in_assembly_gap` where a guide's
absence is better explained by missing assembly than by a differing allele —
always filter on it before reading a hemizygous or missing call as biology.

## Key outputs

Both `analyze_*.py` scripts write into `results/` by default, which is
gitignored. The pipeline script writes into whatever output directory you pass
it. Selected files:

- `guide_exact_match_summary_trim1bp.tsv.gz` — one row per guide with per-
  reference exact-match counts, formatted alignment strings, and the match
  category.
- `unique_trimmed_spacer_membership.tsv.gz` — per unique 19-mer presence/absence
  in each reference.
- `K562_missing_intended_MHC_guides_trim1bp.tsv` and
  `..._guide_clusters_trim1bp.tsv` — the lost guides and the contiguous
  intervals they fall into.
- `K562_intended_MHC_loss_by_10kb_window_trim1bp.tsv` and the matching `.png`
  bar plots — loss counts and loss fraction along chr6.
- `K562_found_vs_missing_by_plot_window.tsv` — per 100-kb window: guides found
  and missing, the losses expected from library density alone, the enrichment
  ratio, and a BH-corrected binomial p-value for excess loss.
- `K562_found_vs_missing_grouped_dual_axis.png` — found and missing guides as
  grouped bars, found on the left axis and missing on the right. The two
  y-scales are independent, so **bar heights are not comparable between the two
  series**; use it to read each distribution's shape, not their ratio.
- `K562_missing_observed_vs_expected.png` — the same windows on a single scale:
  observed losses against the number expected if the loss rate were uniform.
  This is the figure that distinguishes a real loss hotspot from a window that
  simply contains a lot of guides.
- `guide_mapping_lookup.tsv.gz` — the per-guide mapping lookup (see above).
- `screen_top_guides_mapping.tsv.gz` — every top-3 guide in every screen with
  its mapping class and whether its DHS–gene pair is a FRACTEL hit.
- `fractel_hits_with_problem_guides.tsv` — just the FRACTEL hits whose top
  guides are screen-relevant problems.
- `screen_problem_guide_summary.tsv` — one row per screen.

## Requirements

- Python 3 with `pandas`, `numpy`, `scipy`, `matplotlib`
- `bowtie2`

## Caveats

- Guides are compared as 19-mers (first base trimmed) and only exact, PAM-
  agnostic matches count — this is a sequence-presence question, not an
  on-target activity prediction.
- No data is tracked in this repo — not the GRCh38 FASTA, the IGVF guide table,
  or the pipeline results. Only code is versioned; supply or regenerate the
  inputs yourself.
- WTC11 is now analysed using both supplied haplotypes; see the WTC11 workflow
  below. The original shell pipeline remains K562 hap2-specific.

## WTC11: both haplotypes

[WTC11_REPORT.md](WTC11_REPORT.md) contains the results and interpretation:
**475 of 11,253 GRCh38 MHC guide rows (4.22%) lack an exact match in both
WTC11 haplotypes**, compared with 841 using hap1 alone or 759 using hap2 alone.
The report also covers loss hotspots, the K562 comparison, and iPSC/NPC screens.

Use the existing environment; no downloads or package installations are performed:

```bash
mamba activate mambaforge
python run_wtc11_analysis.py --threads 8
python validate_wtc11_results.py
```

The driver uses `data/wtc11.hap1.mhc_contigs.fa` and
`data/wtc11.hap2.mhc_contigs.fa`, the IGVF guide table, and cached GRCh38
alignments. It checks regenerated spacer IDs against the previous per-guide
summary. Cached K562 alignments and `data/manuscript/` supply the comparisons.
All results are written under `results/wtc11/`; existing K562 results are preserved.

Open [alignspacerSeq_WTC11.ipynb](alignspacerSeq_WTC11.ipynb) using the
`mambaforge` Python kernel to run the workflow or inspect its outputs.
`--reuse-alignments` skips alignment after verifying input hashes against the
saved manifest. `--skip-dendrogram` omits the quadratic-memory sequence clustering.
The WTC11 driver additionally requires a SciPy version providing
`scipy.stats.false_discovery_control`, available in the current environment.

Both shared downstream scripts accept `--cell-line WTC11`:
`build_guide_mapping_lookup.py` additionally requires explicit `--hap1` and
`--hap2` alignment tables, and `check_problem_guides_in_screens.py` accepts
`--screens ipsc npc`. The driver supplies these arguments automatically.
The default K562 output schema remains unchanged.

WTC11 retains **all** exact non-supplementary loci, including secondary hits,
and reports hap1, hap2 and their union. Spatial outputs use 10-kb windows and
clusters, plus 100-kb observed-versus-expected plots with full BH adjustment.
The original primary-only summary and older BH calculation remain in the
historical K562 scripts; the WTC11 driver does not use them.

The supplied FASTAs contain whole MHC-bearing contigs (61.7 and 32.3 Mb), not
MHC-only slices. No exact match means absent from these supplied sequences.
`absence_in_assembly_gap` and `hemizygous_WTC11` retain the historical schema,
but mean low nearby guide-match coverage and single-haplotype sequence presence,
respectively; neither establishes an assembly gap, genotype or guide activity.
